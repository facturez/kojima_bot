# Kojima Bot: дизайн исправлений и безопасной оптимизации

## Цель

Устранить подтверждённые ошибки и риски безопасности, повысить тестируемость и надёжность бота, не меняя его основные пользовательские сценарии и не выполняя масштабную архитектурную переработку.

## Границы работы

В работу входят:

- сохранение текущего текста команды `!зов` и использование часового пояса `Europe/Moscow`;
- удаление незавершённого метода `getFarAvay`;
- переход авторизации `!зов` с изменяемого имени роли на стабильные Discord role ID;
- безопасное поведение при пустом списке разрешённых role ID: доступ остаётся только у администраторов;
- ограничение доступа к `!last` правом `MESSAGE_MANAGE`;
- синхронизация удаления Discord-сообщений с локальным архивом;
- ограниченный срок хранения архивных сообщений, настраиваемый через окружение;
- удаление устаревших записей при запуске и перед чтением архива;
- обновление документации по часовому поясу, хранению данных и минимальным Discord-правам;
- тесты для новой политики авторизации, удаления, retention и вычисления ежедневного сообщения;
- локальные упрощения кода только там, где они непосредственно поддерживают перечисленные изменения.

Не входят:

- slash-команды;
- переход с SQLite на внешнюю базу;
- полная замена JDA-архитектуры;
- изменение текста пользовательских команд, кроме сообщений об авторизации и политике хранения;
- автоматическое изменение прав или ролей на работающем Discord-сервере;
- платформенно-зависимое принудительное изменение Unix file mode из Java.

## Авторизация Discord-команд

Команда `!зов` разрешается администраторам и участникам с явно указанным Discord role ID. Сравнение по имени роли удаляется. Список ID остаётся в `AdminCommandConfig`; пустой список закрывает доступ всем неадминистраторам.

Команда `!last` становится модераторской: она разрешается только участникам сервера с правом `MESSAGE_MANAGE`. В личных сообщениях команда отклоняется. Это отделяет обычного участника канала от оператора архива.

Проверки разрешений выделяются в небольшие функции, которые можно тестировать без отправки реальных Discord-сообщений. Отправка ответа остаётся в `CommandHandler`.

## Жизненный цикл сообщений

`MessageRepository` получает операции:

- удалить сохранённое сообщение по Discord message ID;
- удалить записи старше заданного момента;
- читать последние сообщения только после применения retention.

`MessageListener` обрабатывает события удаления сообщений и удаляет соответствующую запись. Для массового удаления обрабатываются все доступные ID. Если Discord не предоставляет достаточную информацию о старом сообщении, удаление выполняется по известному message ID без попытки восстановить содержимое.

Срок хранения задаётся переменной `MESSAGE_RETENTION_DAYS`; значение по умолчанию — 30 дней. Допустимы только положительные целые значения. Некорректная переменная окружения приводит к понятной ошибке запуска, а не к бесконечному хранению.

Очистка устаревших записей выполняется:

- один раз при инициализации репозитория;
- перед выполнением `!last`, чтобы истёкшие записи не возвращались даже у долго работающего процесса.

Это не требует фонового потока и достаточно для текущего небольшого проекта.

## SQLite и файловые права

Код не будет обещать переносимый `0600` для SQLite, WAL и SHM: корректное управление этими правами зависит от операционной системы, контейнерного UID, umask и volume ACL.

В README добавляется требование запускать бота под отдельным пользователем и использовать приватный каталог данных. Docker-конфигурация проверяется и, если это совместимо с текущей сборкой, переводится на непривилегированного пользователя с отдельным каталогом данных.

## Планировщик

Текущая модель «запланировать ближайшую полночь и после выполнения назначить следующую» сохраняется. Планировщик использует `Europe/Moscow`, поэтому отправка всегда привязана к московской полуночи и не зависит от сезонного перевода часов в часовом поясе хоста.

Тестируемые вычисления даты, номера дня и следующего запуска отделяются от JDA-вызовов. Поведение catch-up остаётся ограниченным первыми 15 минутами суток и не должно повторно отправлять сообщение, если дата уже записана в `scheduler_state`.

## Обработка ошибок

- Ошибки SQLite, влияющие на команды чтения и статистики, не должны необработанно завершать JDA event thread; пользователь получает короткое сообщение, а подробность записывается в stderr.
- Ошибка удаления архивной записи логируется, но не мешает Discord обрабатывать последующие события.
- Ошибка асинхронной отправки или удаления Discord-сообщения получает явный обработчик вместо пустого callback.
- Неверная обязательная конфигурация завершается до подключения бота.

## Тестирование

Тесты строятся вокруг чистых политик и реального временного SQLite-файла:

- роль с совпадающим именем и другим ID не даёт доступ к `!зов`;
- разрешённый role ID даёт доступ;
- пустой список ID закрывает доступ неадминистратору;
- `!last` требует серверного участника с `MESSAGE_MANAGE`;
- удаление по message ID удаляет только нужную запись;
- retention не возвращает истёкшие записи;
- неверный `MESSAGE_RETENTION_DAYS` отклоняется;
- расчёт ежедневного сообщения сохраняет текущую базовую дату и номер;
- расчёт следующего запуска корректен для `Europe/Moscow` независимо от часового пояса хоста.

Перед завершением выполняются полный `mvn test` и `mvn package`. Если Maven недоступен, используется Maven Wrapper; если wrapper отсутствует, это фиксируется как внешний блокер, а компиляция проверяется доступными средствами без заявления о полном прохождении тестов.

## Документация и совместимость

Оба существующих README синхронизируются. Документация:

- указывает `Europe/Moscow`;
- объясняет `MESSAGE_RETENTION_DAYS`;
- перечисляет минимальные права: просмотр канала, отправка сообщений, чтение истории там, где нужен `!last`, управление сообщениями для модераторов и `Mention Everyone` только для каналов с `!зов`;
- явно не рекомендует `Administrator`;
- описывает настройку role ID для `!зов`;
- предупреждает о приватном каталоге SQLite и правах volume.

Существующие имена команд, формат ежедневного сообщения, базовая дата, счётчик и пользовательский текст `!зов` сохраняются.
